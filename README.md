# Disagreement Protocol

Локальный инструмент для генерации протокола разногласий из `.docx`-договора с правками Word Track Changes.

Приложение состоит из:

- `backend/` - FastAPI + SQLite, OOXML-пайплайн и экспорт DOCX. Загруженные файлы и база лежат в `backend/data/`.
- `frontend/` - Next.js UI для загрузки документа, проверки сторон, редактирования таблицы и экспорта.
- `desktop/` — оболочка Electron для Windows и macOS со встроенным Python-движком и статической сборкой React-интерфейса. [Установка, сборка и ограничения предварительной версии](desktop/README.md).

Внешних сервисов нет: не нужны Docker, PostgreSQL, Redis и S3. Разбор документа выполняется фоновой задачей FastAPI в том же процессе.

## Требования

Ниже описан запуск для разработки. Пользователям настольной версии устанавливать Python и Node.js не требуется.

- Python 3.12. Рекомендуется именно 3.12: тесты и зависимости проекта рассчитаны на эту ветку.
- `uv` для Python-зависимостей.
- Node.js 22.19+ и npm.

Входной файл должен быть `.docx` без макросов, желательно с правками в режиме рецензирования. `.doc` не поддерживается. Максимальный размер файла — 25 MiB (26 214 400 байт).

## Быстрый запуск

### Автоматически

Из корня проекта:

```bash
./scripts/install.sh
./scripts/start.sh
```

`install.sh` ставит backend-зависимости на Python 3.12 и frontend-зависимости. `start.sh` запускает FastAPI и Next.js в одном терминале.

Откройте `http://localhost:3000`. Для остановки нажмите `Ctrl+C` в терминале со `start.sh`.

### Вручную

#### 1. Установить и запустить backend

```bash
cd backend
uv sync --frozen --python 3.12 --extra dev
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Схема базы создаётся и обновляется автоматически при старте. Обновление добавляет недостающие поля, не удаляя документы и ручные правки. SQLite-файл и загруженные документы появятся в `backend/data/`.

Проверка:

```bash
curl http://localhost:8000/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

#### 2. Запустить frontend

В отдельном терминале:

```bash
cd frontend
npm ci
npm run dev
```

Откройте `http://localhost:3000`.

Frontend обращается к `/api/*`; Next.js проксирует эти запросы на `http://127.0.0.1:8000/api/*`. Оба сервера слушают только `127.0.0.1`, включая `npm start`; приложение не предназначено для публикации в сети. Запросы с посторонними Host/Origin отклоняются. Локальный `curl` без Origin поддерживается.

### Настройки

Локальные значения по умолчанию зашиты в backend и совпадают с `.env.example`. Переопределить можно через файл `backend/.env`:

```bash
DATABASE_URL=sqlite:///./data/disprot.db
STORAGE_DIR=./data/files
```

## Как пользоваться

1. Откройте `http://localhost:3000`.
2. Перетащите `.docx` с Track Changes в область загрузки или выберите файл через кнопку.
3. После обработки откроется подтверждение сторон. Основные замечания видны сразу; статистика и диагностика доступны в «Подробностях обработки документа».
4. Проверьте названия и роли двух сторон. Если распознать их не удалось, заполните предложенные поля вручную. Отметьте нашу сторону и нажмите `Построить протокол`.
5. Проверьте протокол в одном из двух режимов:
   - **По пунктам** — навигация и поиск слева, две редакции с подсветкой различий, согласованная редакция ниже. Предупреждения показаны рядом с соответствующим пунктом.
   - **Таблица** — общий обзор всех строк с закреплёнными заголовками и редактированием ячеек.
6. Нажмите на текст для редактирования. Сохранение происходит при выходе из поля или по Ctrl/⌘+Enter; Esc отменяет текущую правку. При ошибке текст остаётся в редакторе. Смена пункта, режима, переход по навигации и экспорт ожидают сохранения.
7. При необходимости добавьте строку, объедините соседние или исключите строку через меню действий. Смена стороны доступна в панели редактора.
8. Нажмите `Скачать DOCX`, укажите имя файла в диалоге и нажмите `Сохранить`. Редактор остаётся открытым.

Отметки «Проверено мной» сохраняются в текущем браузере отдельно для каждого протокола и конкретной редакции пункта. Изменение текста или стороны делает прежнюю отметку неприменимой. Это личные отметки: они не экспортируются в DOCX и не заменяют автоматическую проверку полноты. При недоступном хранилище отметки действуют до закрытия страницы.

Итоговый документ экспортируется как `.docx` с таблицей протокола разногласий.

Новые пункты получают номер из предложенной редакции — набранный в тексте или вычисленный по автоматической нумерации Word. Если номер определить невозможно, используется «Новый пункт N». Существующие и удалённые пункты сохраняют номера исходной редакции; после вставки при автоматической нумерации номер нового пункта может совпасть с исходным номером следующего.

## Как лучше проверить работу

GitHub Actions запускается только вручную: **Actions → CI (manual) → Run workflow**. Push и pull request не запускают CI. Ручной workflow проверяет тесты backend, тесты и линтер frontend, а также production-сборку.

### Минимальная автоматическая проверка

Backend:

```bash
cd backend
uv run python --version
uv run pytest
```

Версия Python должна быть `3.12.x`. Если `uv` использует другое уже созданное окружение, пересоздайте backend-окружение на Python 3.12 и повторите `uv sync --frozen --python 3.12 --extra dev`.

Frontend:

```bash
cd frontend
npm test
npm run lint
npx tsc --noEmit
```

Production-сборка frontend:

```bash
cd frontend
npm run build
```

### Рекомендуемая ручная проверка

Лучше всего проверять приложение на реальном `.docx`, созданном в Word или LibreOffice:

1. Создайте небольшой договор на русском языке.
2. Включите Track Changes / режим рецензирования.
3. Сделайте несколько разных правок:
   - вставка текста внутри пункта;
   - удаление текста;
   - добавление нового пункта;
   - удаление пункта целиком;
   - правка в пункте с автоматической нумерацией `1.1`, `1.2` и т.п.
4. Загрузите файл в UI.
5. Проверьте, что статус доходит до предварительного отчёта, а не остаётся на анализе.
6. Проверьте, что стороны извлечены или могут быть исправлены вручную.
7. Постройте протокол и сравните строки таблицы с исходными правками в Word.
8. Отредактируйте одну строку, добавьте одну строку и удалите одну строку.
9. Экспортируйте DOCX.
10. Откройте экспортированный файл и убедитесь, что:
    - есть таблица с 4 колонками;
    - номера пунктов соответствуют исходному договору;
    - исходная и предлагаемая редакции попали в правильные колонки;
    - ручные правки из UI сохранились;
    - имя файла корректное и заканчивается на `.docx`.

### Быстрая API-проверка

Когда backend запущен:

```bash
curl http://localhost:8000/health
```

Загрузка документа через API:

```bash
curl -F "file=@/absolute/path/to/contract.docx" \
  http://localhost:8000/api/documents
```

Ответ содержит `id`. По нему можно смотреть анализ:

```bash
curl http://localhost:8000/api/documents/<document-id>/analysis
```

Если `status` стал `parsed`, пайплайн отработал корректно.

## Частые проблемы

- `curl /health` не отвечает - проверьте, что `uvicorn` запущен на порту `8000`.
- UI загружается, но API падает - проверьте backend и rewrite в `frontend/next.config.mjs`.
- Документ висит на анализе - смотрите лог `uvicorn`: пайплайн выполняется фоновой задачей в том же процессе, ошибка будет в логе, а статус документа станет `failed` с текстом ошибки в `/analysis`.
- Приложение завершилось во время разбора — при следующем запуске незавершённые документы получают статус `failed` с объяснением. Загрузите такой исходный файл повторно. Обработанные документы и ручные строки остаются на месте.
- Перед обновлением приложения остановите оба сервера и сделайте копию `backend/data/` (или своих `DATABASE_URL`/`STORAGE_DIR`). Не удаляйте базу ради обновления схемы: встроенная миграция сохраняет данные. Для отката к старой версии кода используйте копию.
- В старой базе может не быть порядка блоков. При построении он восстанавливается из исходного DOCX, если сохранены идентификаторы абзацев и исходный файл. Иначе показывается предупреждение; ранее созданные строки с ручными правками автоматически не перестраиваются.

## Границы обработки

Разбор и экспорт выполняются локально. Поддерживаются текстовые вставки/удаления, `moveFrom`/`moveTo`, вставки/удаления строк и ячеек таблицы, а также `lvlRestart` нумерации. Неполные пары перемещений помечаются предупреждением. Правки объединения ячеек (`cellMerge`) и вложенные таблицы требуют предварительной обработки в Word: приложение сообщает о неподдерживаемой конструкции.

Проверка полноты сопоставляет исходные правки с происхождением строк. Объединение сохраняет все исходные пункты; удаление строки или очистка обеих редакций уменьшает покрытие. Это проверка наличия правок, а не юридической корректности вручную изменённого текста. При смене стороны обновляется автоматическая согласованная редакция; явно отредактированная сохраняется. Для старых строк без отдельного признака редактирования согласованной редакции приложение консервативно сохраняет строки с `user_edited`.

Ограничения проверяются до обработки опасных данных:

- HTTP-тело загрузки — 26 MiB, один файл `file`, без дополнительных файлов и текстовых полей; чтение запроса — до 30 секунд. Остальные изменяющие API-запросы — до 4 MiB.
- Одновременно принимаются до двух загрузок, фоновый разбор выполняется по одному документу. Это режим одного процесса Uvicorn; несколько workers для него не поддерживаются.
- ZIP — до 2048 записей, 32 MiB на распакованную часть и 128 MiB суммарно. Количество записей проверяется до создания объектов ZIP. Дубликаты, шифрование, многотомные архивы, ZIP64 и сжатие кроме Store/Deflate отклоняются.
- Основной XML — до 16 MiB; все читаемые XML — до 26 MiB. Размер, CRC и конец сжатого потока проверяются независимо от заявленного размера ZIP-записи. Бюджет сложности — 250 000 элементов/атрибутов/служебных узлов, глубина — 128. Общий бюджет времени — 10 секунд: проверки выполняются между стадиями и внутри циклов обработки, включая уже построенное дерево. Это кооперативный дедлайн, без принудительного завершения системного процесса. DTD запрещён независимо от кодировки; внешние сущности и сеть выключены.
- `numbering.xml` и `styles.xml` размером свыше 5 000 000 байт не разбираются; причина пропуска отображается в диагностике. Остальные ограничения архива действуют и для них.

Next 15.5.24 настроен на 27 MiB при клонировании тела запроса: это оставляет backend возможность вернуть 413 до усечения потока. Общая версия PostCSS 8.5.26 закреплена через `overrides`, включая зависимость Next. Версии runtime-зависимостей закреплены в `package-lock.json` и `uv.lock`; установка по lock-файлам воспроизводима.
