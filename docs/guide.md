# Руководство по работе

[← Главная страница](../README.md) · [Установка и сборка](../desktop/README.md)

«Протокол разногласий» — настольное приложение для Windows и macOS. Интерфейс, обработка договоров и экспорт работают локально; готовому приложению не нужны Python, Node.js, Microsoft Word или интернет.

## Установка и запуск

Используйте EXE для Windows или DMG для macOS. [Получение установщиков, запуск из исходников и проверка сборки](../desktop/README.md).

Входной файл — `.docx` без макросов, до 25 MiB (26 214 400 байт), с правками Word Track Changes. Формат `.doc` не поддерживается.

## Как пользоваться

1. Запустите приложение «Протокол разногласий». Договоры, открытые ранее в этом профиле приложения, перечислены в разделе «Недавние документы»: ссылка возвращает на нужный этап, крестик убирает запись только из списка (файл и данные на диске не трогаются).
2. Перетащите `.docx` с Track Changes в область загрузки или выберите файл через кнопку.
3. После обработки откроется подтверждение сторон. Основные замечания видны сразу; статистика и диагностика доступны в «Подробностях обработки документа».
4. Проверьте названия и роли двух сторон. Если распознать их не удалось, заполните предложенные поля вручную. Отметьте нашу сторону и нажмите `Построить протокол`. Пока кнопка недоступна, рядом перечислено, чего не хватает.
5. Проверьте протокол в одном из двух режимов:
   - **По пунктам** — навигация и поиск слева, фильтр «Все пункты / Требуют внимания / Не проверены мной» со счётчиками, две редакции с подсветкой различий, согласованная редакция ниже. Предупреждения показаны рядом с соответствующим пунктом.
   - **Таблица** — общий обзор всех строк с закреплёнными заголовками и редактированием ячеек.
6. Нажмите на текст для редактирования. Сохранение происходит при выходе из поля или по Ctrl/⌘+Enter; Esc отменяет текущую правку. При ошибке текст остаётся в редакторе. Смена пункта, режима, переход по навигации и экспорт ожидают сохранения.
7. `Проверено — дальше` ставит отметку «Проверено мной» и открывает следующий пункт; обычный `Следующий пункт` отметку не ставит. С фильтром «Не проверены мной» так удобно пройти весь протокол.
8. При необходимости добавьте строку, объедините соседние или исключите строку через меню `…` у пункта (закрывается по Esc и клику вне). Исключение требует подтверждения и не отменяется. Смена стороны доступна в панели редактора.
9. Во вкладке **Оформление** заполните название и реквизиты договора, место и дату протокола. Отредактируйте типовой текст перед таблицей или вставьте собственную шапку; ниже доступны названия всех четырёх колонок и заключительные положения. Предпросмотр показывает содержание документа без разбиения на страницы.
10. Заполните подписи: наименования и роли сторон уже подставлены, должности и ФИО вводятся вручную. Выберите, от какой стороны составляется протокол. Под её подписью по умолчанию появится «С учетом протокола разногласий»; отметку можно отключить. Выбор стороны связан с «нашей стороной» в таблице. Подписанты привязаны к конкретным сторонам и не теряются при их смене.
11. Нажмите `Сохранить оформление` либо перейдите к правкам / скачиванию — приложение сначала сохранит форму. При ошибке введённый текст остаётся в форме, а переход и экспорт блокируются до успешного сохранения. Типовую шапку, заключительные положения и названия колонок можно восстановить отдельными кнопками. Незавершённые изменения защищены предупреждением при закрытии приложения.
12. Нажмите `Скачать DOCX`, укажите имя файла в диалоге и нажмите `Сохранить`. Редактор остаётся открытым.

Отметки «Проверено мной» сохраняются в текущем профиле приложения отдельно для каждого протокола и конкретной редакции пункта. Изменение текста или стороны делает прежнюю отметку неприменимой. Это личные отметки: они не экспортируются в DOCX и не заменяют автоматическую проверку полноты. При недоступном хранилище отметки действуют до закрытия приложения.

Итоговый `.docx` содержит шапку, вводный текст, таблицу, заключительные положения и подписи. Формат — A4, альбомная ориентация; заголовки таблицы повторяются на следующих страницах. Незаполненные дата, место и подписанты остаются строками для заполнения. Тексты формы редактируются обычным текстом с переносами строк; форматирование из Word не переносится.

Оформление хранится в локальной базе вместе с протоколом. Для ранее созданных протоколов типовая форма подставляется без перестроения строк и потери правок. Изменение названий колонок не меняет содержимое редакций. Автоматические названия следуют выбранным сторонам; вручную заданные остаются до сброса. Своя шапка сохраняется при смене сторон; проверьте указанные в ней реквизиты. Имена и роли в типовой шапке следуют данным блока подписей.

Новые пункты получают номер из предложенной редакции — набранный в тексте или вычисленный по автоматической нумерации Word. Если номер определить невозможно, используется «Новый пункт N». Существующие и удалённые пункты сохраняют номера исходной редакции; после вставки при автоматической нумерации номер нового пункта может совпасть с исходным номером следующего.

## Данные и резервная копия

Через **Файл → Открыть папку данных** можно открыть SQLite-базу и загруженные договоры. Обновление приложения сохраняет данные; Windows-деинсталлятор их не удаляет.

- macOS: `~/Library/Application Support/DisagreementProtocol/data`.
- Windows: `%APPDATA%\DisagreementProtocol\data`.

Закройте приложение перед копированием. Для полной резервной копии сохраните весь каталог `DisagreementProtocol`, поскольку личные отметки проверки находятся в профиле Electron рядом с `data`. Данные исходного договора и ручные редакции хранятся в локальной базе.

Запуск Electron из исходников использует стандартный профиль приложения. Для тестов можно задать отдельный абсолютный путь через `DISPROT_USER_DATA`; инструкция есть в [руководстве сборки](../desktop/README.md#локальная-сборка).

## Проверка на своём договоре

1. Создайте договор в Word или LibreOffice с режимом рецензирования.
2. Добавьте вставку и удаление текста, новый пункт, удаление пункта и правку автоматической нумерации.
3. Загрузите файл в приложение, проверьте стороны и постройте протокол.
4. Сравните строки с исходными правками; отредактируйте строку, добавьте новую и объедините соседние.
5. Задайте оформление, подписи и сохраните DOCX через системный диалог.
6. Откройте DOCX и проверьте номера, четыре колонки, редакции сторон, ручные правки и подписи.
7. Закройте приложение, откройте его снова и убедитесь, что договор и правки сохранились.

## Частые проблемы

- **Приложение не запускается.** Для запуска из исходников сначала выполните `prepare:app`. Если установленное приложение сообщает об ошибке движка, перезапустите его; при повторении ошибки переустановите. Сохранённые документы находятся отдельно от установщика.
- **Документ не обработался.** Приложение показывает причину ошибки. Проверьте формат файла и диагностику, затем загрузите исходный договор повторно.
- **Приложение закрылось во время разбора.** При следующем запуске незавершённый документ получит статус ошибки. Загрузите исходный файл повторно. Обработанные документы и ручные строки остаются на месте.
- **Не удалось сохранить DOCX.** Повторите экспорт и выберите доступную папку в системном диалоге сохранения.
- **Нужно обновить приложение.** Закройте его и сделайте резервную копию профиля. Не удаляйте базу: встроенная миграция обновляет схему с сохранением документов и правок. Для отката к прежней версии используйте резервную копию.
- **В старой базе отсутствует порядок блоков.** Он восстанавливается из исходного DOCX, если сохранились файл и идентификаторы абзацев. Иначе приложение показывает предупреждение; ранее созданные строки с ручными правками автоматически не перестраиваются.

## Границы обработки

Разбор и экспорт выполняются локально. Поддерживаются текстовые вставки/удаления, `moveFrom`/`moveTo`, вставки/удаления строк и ячеек таблицы, а также `lvlRestart` нумерации. Неполные пары перемещений помечаются предупреждением. Правки объединения ячеек (`cellMerge`) и вложенные таблицы требуют предварительной обработки в Word: приложение сообщает о неподдерживаемой конструкции.

Проверка полноты сопоставляет исходные правки с происхождением строк. Объединение сохраняет все исходные пункты; удаление строки или очистка обеих редакций уменьшает покрытие. Это проверка наличия правок, а не юридической корректности вручную изменённого текста. При смене стороны обновляется автоматическая согласованная редакция; явно отредактированная сохраняется. Для старых строк без отдельного признака редактирования согласованной редакции приложение консервативно сохраняет строки с `user_edited`.

Ограничения проверяются до обработки опасных данных:

- HTTP-тело загрузки — 26 MiB, один файл `file`, без дополнительных файлов и текстовых полей; чтение запроса — до 30 секунд. Остальные изменяющие API-запросы — до 4 MiB.
- Одновременно принимаются до двух загрузок, фоновый разбор выполняется по одному документу. Это режим одного процесса Uvicorn; несколько workers для него не поддерживаются.
- ZIP — до 2048 записей, 32 MiB на распакованную часть и 128 MiB суммарно. Количество записей проверяется до создания объектов ZIP. Дубликаты, шифрование, многотомные архивы, ZIP64 и сжатие кроме Store/Deflate отклоняются.
- Основной XML — до 16 MiB; все читаемые XML — до 26 MiB. Размер, CRC и конец сжатого потока проверяются независимо от заявленного размера ZIP-записи. Бюджет сложности — 250 000 элементов/атрибутов/служебных узлов, глубина — 128. Общий бюджет времени — 10 секунд: проверки выполняются между стадиями и внутри циклов обработки, включая уже построенное дерево. Это кооперативный дедлайн, без принудительного завершения системного процесса. DTD запрещён независимо от кодировки; внешние сущности и сеть выключены.
- `numbering.xml` и `styles.xml` размером свыше 5 000 000 байт не разбираются; причина пропуска отображается в диагностике. Остальные ограничения архива действуют и для них.

Зависимости закреплены в `package-lock.json` и `uv.lock`; сборка устанавливает их по lock-файлам.
